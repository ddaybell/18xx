- [x] **2g. There is no separate pre-game auction round at all** — corrected twice by the user before landing on the actual design. First correction: leftovers don't hand off to ordinary Stock-round play (they get re-auctioned). Second, more fundamental correction: the "first SR" *is* a normal Stock round, not a distinct Auction round that later hands off to one -- it just happens to also carry the waterfall-bidding step. As long as no one triggers an all-pass, the round stays open exactly like any SR: once the last company sells (via direct buy or a resolved bid), a turn simply flows straight into ordinary share-buying with no round transition at all.   - `Game#stock_round` now includes `Engine::Step::CompanyPendingPar`/`G2038::Step::WaterfallAuction` ahead of `BuySellParShares` -- WaterfallAuction blocks a turn (bid/pass on companies) for as long as any remain, and its own `actions` goes empty the instant `@companies` is, at which point that same turn (or the next) flows straight into ordinary share buying with no extra step to pass through.
  - `next_round!` is back to the plain, uniform 3-case Stock/Operating structure with no Auction-round special-casing at all -- since `init_round` is now a real `Engine::Round::Stock`, the existing `when Engine::Round::Stock` branch already handles the very first round's ending uniformly with every later one.
  - `Game#initial_auction_companies` stays overridden (`owner.nil? && !closed?`) -- still needed since a fresh `WaterfallAuction` step instance is built for every new Stock round and must only re-list what's actually still unsold.
  - Discovered mid-fix: `Round::Stock#start_entity` re-runs **every** step's `setup` at the start of each entity's turn, not just once per round. The base `WaterfallAuction#setup` (`setup_auction` → `@bids = Hash.new{...}`) would silently wipe out bids placed by earlier players in the same round every time the next player's turn began. Fixed with a guard (`return if @bids`) so only the first call for a fresh step instance actually initializes anything.
  - `WaterfallAuction#round_end_auction_complete` is now nearly empty (`@process_round_end_auction = false`) -- no clearing `@companies` (leftovers just stay in place, still unowned, to be re-offered on a later turn or round), no unpassing entities (needed so `Round::Stock#finished?`'s own all-entities-passed check can actually fire), and no `payout_companies`/`or_set_finished` call (that would double-pay every owned company's revenue on top of the normal payout `Round::Operating#setup` already does at the start of the OR set that follows).
  - Second bug found via testing, not by inspection: when an all-pass resolves into a still-pending mini-auction (a bid-upon company had 2+ bids), `Round::Stock#finished?` would see every entity's `.passed?` flag still true (nothing had unpassed them yet) and consider the round over *immediately*, ending it out from under the pending resolution before the mini-auction's bidders ever got to act. Fixed in `resolve_bids`: only when `all_bids_processed?` is genuinely true does `round_end_auction_complete` fire; otherwise `entities.each(&:unpass!)` keeps the round open until the mini-auction (and anything still queued behind it) actually resolves down.
  - Verified via script against the real action-processing pipeline (`game.process_action`, not the individual methods in isolation): bids placed on separate players' turns survive to the next turn instead of being wiped; a company bought directly (no bidding) doesn't end the round -- the same round continues into ordinary share buying; an all-pass with one single-bid and one multi-bid company correctly keeps the round open through the mini-auction's own resolution and only *then* transitions to the OR set; a later Stock round (after that OR set) correctly re-offers exactly what's still unsold. *(post-Phase-11 fix, supersedes both the original 2d and the first pass at 2g)*
- [x] **2e. Auction ordering** — confirmed via manual playtesting that companies sell in order "0" through "11"; no automated test added. *(verified manually)*

- [x] **4a. Hex-based movement model** — trace-based: one MP per hex entered; `choices` in the route step offers only adjacent hexes while MP remain; `route_distance` = `route.hexes.size - 1`; `route_distance_str` shows "3H" etc. *(PR4)*
- [x] **4b. Dual constraint enforcement** — MP limit enforced per click (illegal moves are simply not offered, and `process_choose` raises on hand-crafted invalid choices); pickup choices are only offered while a cargo hold is free. *(PR4)*
- [x] **4c. Route origin/destination rules**: *(PR4)*
  - [x] Route must **start** at one of the company's own bases — `start_choices` offers only the entity's placed token hexes *(PR4)*
  - [x] Route must **end** at any base OR a transshipment point to deliver — `trace_revenue` gates on `deliverable_destination?(trace.last)`; undelivered loads are lost (logged); exploring-only routes earn $0 *(PR4)*
  - [x] Ending at a transshipment point with an **empty** cargo hold earns its printed (transshipment) value; visiting one mid-route pays nothing *(PR4)*
  - [x] **Transshipment pickup is a player choice, not automatic** — confirmed with the user: the rules permit a ship to end its flight at a transshipment point *without* collecting there, so `pick_up_transshipment!` is no longer called from `launch_at`/`move_to` on arrival. Instead `transshipment_choice` (mirrors `pickup_choices`) offers a `TRANSSHIP` choice whenever the current hex is a transshipment point with a free cargo hold, aliased onto a click on the current hex itself exactly like a mine pickup (`alias_current_hex_pickup!` now treats `PICKUP`/`TRANSSHIP` as one combined "exactly one -> alias it" pool). Confirmed with the user that choosing to collect also immediately ends the flight (`process_choose`'s `TRANSSHIP` branch calls `pick_up_transshipment!` then `finish_route` together, unlike an ore pickup which lets the ship keep flying) — a side effect of this is that a transshipment credit can now only ever be picked up at the route's actual ending hex, never mid-route, which already matches the pre-existing revenue rule above. `maybe_auto_finish!` (MP-exhausted auto-completion) now also holds off if a transshipment choice is still pending, same as it already did for ore pickups. Verified via script against the real step (`compute_choices`/`process_choose`), not just the isolated method. *(post-Phase-4 fix)*
- [x] **4d. Refueling station bonus** — when a ship belonging to the owning corporation enters a refueling station hex, remaining MP is bumped by up to 3 (capped at the ship's max) — `Step::Route#refuel!`, called from `move_to` when `Game#refueling_station_owner(hex.id) == entity` and not already refueled at that hex this flight; `Game#hexes_in_range` applies the same top-up when computing reachability. *(PR5, checkbox was stale)*
- [x] **4e. Used Mine enforcement** — the Used Mine marker is placed at pickup time (`mark_mine_used!`); cancelling a route returns its loads and un-marks their mines; `or_round_finished` resets the flags each OR *(PR4)*
- [x] **4f. Claimed mine access** — pickup choices skip mines claimed by others; `pickup_value` pays claimed value to the owner *(PR4; claim placement is Phase 5)*
- [x] **4g. Loads cannot be jettisoned, so an early pickup can block a better mine found later in the run. Cargo aboard is shown in the step help text. *(PR4)*
- [x] **4h. Exploration mid-route** — implemented via the **choose-per-hex model** (supersedes the earlier blended client/server design): *(PR4)*
  - [x] Route tracing uses the standard `choose` action pattern — each hex click fires `Action::Choose` with the hex id (`assets/app/view/game/hex.rb` choose hook); the trace accumulates in `G2038::Step::Route` state and replays deterministically. No engine changes; no node/path-walking (which explodes on 2038's junction hexes). *(PR4)*
  - [x] Only legal next hexes (adjacent to trace tail, MP remaining) are clickable — `available_hex` = `choices` membership; choice buttons mirror map clicks; traced hexes highlight via `@round.laid_hexes` *(PR4)*
  - [x] Entering an unexplored blue hex reveals its pre-assigned tile **immediately mid-route** — the player sees the mines before choosing the next hex *(PR4)*
  - [x] Owning company receives $10 exploration bonus to treasury (not route revenue) *(PR4)*
  - [x] Previously explored hexes are traversed at normal MP cost *(PR4)*
  - [x] Per-hex undo comes free — each hex click is one engine action *(PR4)*
  - [x] Route completion (`finish` choice) computes revenue via `trace_revenue`/`trace_pickups` (greedy, cargo-hold-capped, delivery-gated), builds a passive `Engine::Route` (seeded `hexes:`/`revenue:`; never path-walks) for the dividend step, and logs the run *(PR4)*

  - [x] **"Fly over without exploring" choice** — entering an unexplored hex now offers two options whenever affordable: `hex.id` ("Explore", 2 MP: 1 fly + 1 explore) and `flyover_<hex.id>` (1 MP, tile stays hidden, no mine access, no bonus). Since flyover never costs more than explore, if `hex.id` is offered `flyover_<hex.id>` always is too. *(PR4)*
  - [x] **Hex-anchored popup for the explore/flyover choice** — clicking the hex directly on the map (rather than the bottom choice panel) shows a small "Explore"/"Fly over"/✖ popup positioned at the hex, mirroring `tile_confirmation.rb`'s look exactly. Built as a **generic, opt-in extension** (`G2038::Step::Route#hex_choice_popup(entity, hex)`, `Lib::HexChoicePopup`, `View::Game::HexChoicePopup`) — every other game's `step.respond_to?(:hex_choice_popup)` is false, so behavior is unchanged for them. **This piece touches two shared frontend files (`hex.rb`, `map.rb`) and should be submitted as its own PR** so reviewers can evaluate the core-file tweak in isolation from the rest of PR4/5. *(PR4, split out for review)*
  - [ ] Server-game ergonomics: one HTTP POST per hex click (fine for hotseat; revisit before live play) *(PR5+)*
- [x] **4i. Exploration undo policy** — see Architectural Decision B. In-step cancel is already blocked after exploration (4h); the engine-level **Undo** button cannot be blocked (it rebuilds the game from `@raw_actions` with no game-specific hook to intercept it), so instead: whenever an undo reaches back far enough to un-happen an exploration, log a permanent warning naming the player and hex — confirmed with the user this should announce the peek without disclosing what was actually found, so the fix doesn't broaden the hidden-information leak beyond what the peek itself already caused.
  - **Detection**: reuses `Game::Base.filtered_actions` itself (the exact logic that already decides what an undo removes) rather than guessing from the raw action's shape, as originally sketched — run it once on `@raw_actions` and once with the incoming undo appended; whichever action ids flip from kept to undone are what this undo actually removes. Cross-referencing those ids against `@log` (`GameLog::Entry#action_id` already tags every line with the action that produced it — the user's own suggestion, and the key simplification over the original plan) finds any `"<entity> explores <hex>:"` line among them, with no need for a second full game replay.
  - **Persistence**: the check has to run using the *pre-undo* instance's still-intact `@log`, since an `Action::Undo` short-circuits `Game::Base#process_action` into `clone(@raw_actions)` — a brand new `Game` instance replayed from scratch — rather than mutating the current one. The resulting warning is appended as a genuine follow-up `Action::Message` on the *returned* (post-undo) instance, since `Action::Message` is the one action type `filtered_actions` guarantees can never itself be undone (`when 'message'`) — so it's not just a live-moment notice, it's baked into the action history and reappears identically on every future reload of the game. Verified via script: reloading a game fresh from its raw actions reproduces the exact same warning.
  - **Two real bugs found only by testing this end-to-end, not by inspection**: (1) `entity_type` mismatch — `Step::Message#actions` requires a player entity, but `action.entity` for an in-OR undo is often a corporation; fixed by resolving through `Game::Base#acting_for_entity` (the corp's president) the same way the rest of the game already does. (2) `Action::Base#to_h` memoizes its result the first time it's ever called on a given instance (`@_h ||= {...}`) — the detection logic's own `.to_h` call on the incoming undo action, made *before* `Game::Base#process_action` assigns its `id`, permanently cached a hash with the `id` key missing entirely, which then corrupted the real clone's own use of that same `.to_h` call and broke replay for the rest of the game's life ("comparison of Integer with nil failed" in `process_to_action`). Fixed by assigning the id myself (the same value `super` would assign anyway) before the first `.to_h` call happens.

Guarded with `entry.message.is_a?(String)`. *(post-Phase-11 addition, supersedes the original initialize_actions-override sketch)*

## Key Architectural Decisions

### A. Mine revenue model
- [x] **Chosen approach:** Store mine state in a `@mine_state` hash on the game object; pickup logic looks up claimed/unclaimed values dynamically. Tile codes display the real unclaimed value for reference, but revenue is never computed from tile codes. *(PR4)*
- [x] **`MINE_DATA` constant** maps each asteroid tile number (2001–2022) to an ordered array of mine hashes (`{ore:, unclaimed:, claimed:}`). `explore_hex!` merges these with `owner: nil, used: false` into `@mine_state` when a tile is placed. *(PR4)*
- [x] **Bases and mines are mutually exclusive on a hex.** Placing a base flips the tile to 2023 (no mines). `@mine_state` only ever tracks un-based explored hexes. *(PR5)*

### B. Exploration undo policy
- [x] **Chosen approach:** Stay fully faithful to the physical game — asteroid tiles are revealed immediately when explored, mid-route. Undo is **not** blocked. Instead, confirmed with the user: log without disclosing content — any undo that reaches back far enough to un-happen a specific exploration gets a permanent log entry naming the player and the hex (not what was found there), so other players can police suspected peeking without the fix itself broadening the information leak. See Phase 4i for the implementation. *(decision PR4; implementation post-Phase-11)*

  **How the engine works (important context):**
  - When an undo arrives, `Game::Base#process_action` immediately calls `return clone(@raw_actions)` — the game is completely rebuilt from scratch. No game-specific hooks (`preprocess_action`, etc.) fire for undo actions.
  - `@log` is rebuilt from scratch on every clone/undo.
  - `Action::Log` (which extends `Action::Message`) is **never** filtered out by `filtered_actions` — messages survive all undos and are replayed in the correct chronological position.
  - `initialize_actions` is overridable in a game subclass without touching engine code.

  **Implementation approach — override `initialize_actions` in `G2038::Game`:**
  - After calling `super` (which replays all actions and builds `@log`), scan `@raw_all_actions` for any `{ 'type' => 'undo' }` entries
  - For each undo found, look up the player via `action['user']`, identify the action ID range that was undone via `action['action_id']`
  - Append a styled log entry: `"⚠ [UNDO] PlayerName undid action(s) #Y–#Z"`
  - These entries appear at the bottom of the log (not inline), but are permanent — they survive all further undos because they are regenerated fresh on every rebuild

  **Implementation tasks:**
  - [ ] Override `initialize_actions` in `G2038::Game`; after `super`, scan `@raw_all_actions` for undo entries and build log entries *(PR6)*
  - [ ] Only emit undo log entries during Operating Rounds (check round type at the action's point in history, or always log and rely on the action ID range being self-explanatory) *(PR6)*
  - [ ] Format the log entry to include: player name, action ID range undone, and round/turn context if determinable *(PR6)*
  - [ ] Undo announcements must persist even if the player subsequently undoes further actions (guaranteed by the rebuild approach above) *(PR6)*
  - [ ] Investigate whether `self.filtered_actions` override could instead inject a synthetic `message`-type hash at the undo's chronological position, which would make the log entry appear in-order rather than at the bottom — this is a stretch goal if in-order logging matters *(PR6)*

### C. Spaceship distance model and pickup selection
- [x] **Chosen approach (revised PR4): choose-per-hex tracing.** Spaceships stay in TRAINS for purchase/obsolescence tracking. `G2038::Step::Route` inherits `Engine::Step::Base` and traces routes one hex per `choose` action — no node/chain path-walking, no engine changes. `Engine::Route` is used only as a passive container (seeded `hexes:`/`revenue:`) handed to the dividend step. *(PR4)*
- [x] **Pickup selection UX (revised PR4): pickup is a per-hex-entry choice, per the rules.** While a ship sits on a mine hex, `choices` offers a "Pick up X ore" entry per available mine (hold space permitting). Loads cannot be jettisoned once aboard — picking up early can block a better mine found later in the run, which is a real decision the player must make. The Used Mine marker is placed at pickup time; cancelling a route returns its loads and un-marks their mines. *(PR4)*
  - [x] `pickup_value(entity, hex_id, mine_idx)` — returns claimed or unclaimed value *(PR4)*
  - [x] `trace_revenue(entity, train, trace, cargo)` — cargo pays out only when the run ends at a base or transshipment point; ending at a transshipment point with **empty** holds earns its printed value; undelivered loads are lost (logged) *(PR4)*
- [x] **`deliverable_destination?(hex)`** — returns true if hex is a transshipment point or has any placed base token; used by `trace_revenue` to gate delivery *(PR4)*

### D. Unexplored hex representation
- [x] **Chosen approach:** Pre-generate all tile assignments at `setup` using a seeded shuffle of the full tile pool. Store in `@hex_assignments` (hex_id → tile_name, server-side only, never sent to clients). When a ship's `Choose` move enters an unexplored hex, the server looks up the pre-assignment, places the tile, and reveals it to all players simultaneously. *(implemented PR4)*

  **Why pre-generate rather than draw from a live bag:**
  - There are exactly **106 blue hexes and 106 mine tiles** — a perfect 1:1 match, so a complete pre-assignment is always possible.
  - `@hex_assignments` is derived deterministically from `@seed` in `setup`, so it is rebuilt identically on every clone/undo without being stored in `@raw_actions`.
  - Undoing an `ExploreHex` action naturally un-reveals the tile — the game rebuilds from `@raw_actions`, which no longer contains the explore action, so the hex reverts to blue. The pre-assignment in `@hex_assignments` is still intact for the next exploration.
  - `Action::ExploreHex` only needs a hex_id — no tile name, no bag state.
  - No "bag" shrinks over time; no bag state to maintain or serialize.

  **Implementation:**
  - [x] `assign_exploration_tiles` in `setup`: sorted blue hex ids zipped with the TILES-count tile pool shuffled via the engine's deterministic LCG `rand` (identical in Opal/MRI; `Random.new` is not cross-platform-safe) *(PR4)*
  - [x] `explore_hex!(hex_id, entity)`: looks up `@hex_assignments[hex_id]`, lays an unplaced tile copy, updates `@mine_state`, awards the $10 exploration bonus, logs the event. Fired from `process_choose` when a ship enters an unexplored blue hex (no separate `ExploreHex` action needed — the `Choose` move action carries the hex id) *(PR4)*
  - [ ] Verify that `hex.lay` during an OR (outside the normal `LayTile` step) is fully reflected in serialized game state across reload *(PR4 testing)*
  - [x] **Tile counts confirmed correct:** 100 blue hexes, 106 tiles — the 6 surplus tiles are deliberately unassigned spares for second-draw special powers *(PR4)*
  - [x] **Second-draw powers (IF/DH forced redraw, Lucky's two-tile choice):** implemented via `Game#borrow_second_tile` (deterministic `rand`-picked unexplored hex, tile borrowed then whichever isn't used put back) and `Step::Route#resolve_redraw!`/`REDRAW` -- confirmed live in real recorded games (`redraw_first`/`redraw_second` choices throughout Lucky's/Ice Finder's/Drill Hound's flights). Stale checkbox, not tracked as its own PR. *(PR7)*

### E. Infrastructure placement model
- [x] **Bases → Token system.** Tokens occupy a city slot (one base per hex), have placement costs, belong to a corporation, and establish route origins. The 13 pre-printed starting bases map to home tokens at each entity's starting coordinates. *(PR5)*
  - [x] **Independent companies have exactly one base — their home base.** One free home token, no additional tokens. `deliverable_destination?` returns true for any hex with a placed token, so independent bases correctly qualify as delivery destinations for any ship. *(PR4)*
- [x] **Refueling Stations → Modifier on a base.** Will be stored as a `@refueling_stations` hash (`hex_id → corporation`). When any ship owned by the station's corporation enters that hex, remaining MP is increased by 3, capped at the ship's original MP: `new_remaining = [remaining + 3, original_mp].min`. One refueling station per base; usable once per ship per OR. *(PR5)*
- [x] **Claims → Revenue modifier only.** Stored in `@mine_state` as `mine[:owner]`. A claim marks a mine as owned by a specific company; that company's ships earn `mine[:claimed]`, all others earn `mine[:unclaimed]`. Claims have no effect on routing or movement. *(PR4)*
  - [x] **Independent companies each have 2 claims** (not tokens — handled as custom claim state in `@mine_state`). *(PR5)*
- [x] **Bases and claims are mutually exclusive** — enforced by rule (bases require a tile without claims; the tile flip to 2023 removes mines). No code-level guards needed. *(PR5)*
